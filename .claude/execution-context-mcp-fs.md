# Execution Context

## Project Patterns
- UV workspace monorepo with `packages/*` as workspace members
- Each package uses hatchling build system with `src/` layout: `src/package_name/`
- `tool.hatch.build.targets.wheel.packages` must point to `["src/package_name"]`
- Package entry points use Typer apps in `__main__.py` with `app = typer.Typer()`
- Root `pyproject.toml` has `[tool.uv.sources]` mapping each package to `{ workspace = true }`
- Sub-package `__init__.py` files use docstrings describing the module purpose
- Test structure mirrors source: `tests/test_backends/`, `tests/test_tools/`
- Ruff line-length: 100, Python 3.11+, strict mypy
- Error modules follow pattern: ErrorCode class with string constants, ERROR_SUGGESTIONS dict, create_error_response function, custom exception hierarchy
- Utility modules use `from __future__ import annotations` and expose public functions at module level
- Test files organize tests into classes by functional area (e.g. TestDetectMimeTypeCommonExtensions, TestFormatSize)
- Ruff I001 (import sorting) requires blank line between stdlib and third-party imports but NOT between `from __future__` and stdlib
- Pydantic models follow postgres pattern: BaseModel with Field() descriptors, computed_field for derived values, `from __future__ import annotations` for type annotation syntax
- Models __init__.py re-exports all public symbols with __all__ list organized by category
- Ruff UP017 rule requires `datetime.UTC` instead of `timezone.utc` in Python 3.11+
- Config modules follow pattern: pydantic-settings BaseSettings per scope, SettingsConfigDict with env_prefix and env_file="mamba.env", module-level _env_file_path for CLI override, root Settings class with model_validator to load nested, get_settings() factory
- Security module uses helper functions (_sanitize_path, _decode_url_encoding, etc.) exposed at module level, with SecurityValidator class as the main public API
- Backend abstraction uses `typing.Protocol` with `@runtime_checkable` for BackendProtocol interface; BackendManager routes operations by path prefix and validates via SecurityValidator before returning backend instance
- MCP tool functions follow postgres pattern: @mcp.tool() decorator with ToolAnnotations, async function with ctx: Context[ServerSession, AppContext] | None = None, return Pydantic model | dict[str, Any]
- Tool error handling: catch FSError -> create_error_response with exc.code/exc.message; catch Exception -> BACKEND_ERROR; unwrap BackendError.__cause__ to surface original FSError code
- Tool hidden file filtering is a two-layer system: LocalBackend.ls() filters based on config default, then tool layer applies include_hidden override; include_hidden=True cannot restore files already filtered by backend when show_hidden=False
- Tool tests use MagicMock for MCP Context, with ctx.request_context.lifespan_context set to AppContext instance
- Tool functions should pass original user path (not resolved_path from get_backend) to backend.info() and backend.cat_file() so LocalBackend can detect symlinks before resolution
- read_file tool pattern: get backend -> info for size -> check size limit -> cat_file for content -> detect MIME -> encode content (text or base64) -> return ReadFileResponse
- Content encoding helper (_encode_content) uses is_text_content for MIME-based detection; force_base64 checked first (overrides all), then text detection, with fallback to base64 on decode failure
- Size limit enforcement: full reads (no offset/limit) check total_size > size_limit; chunked reads (offset > 0 or limit is not None) bypass the limit check
- Ruff UP012 rule flags unnecessary `.encode("utf-8")` calls; use `b"string"` literals instead
- search_files tool uses iterative BFS traversal with early termination at max_results; regex compiled once upfront; _extract_match_context provides 2 lines before/after with ">" marker on match line
- MockBackend enhanced with set_dir_entries(dir_path, entries) and set_file_contents(path, content) for per-directory/per-file mocking needed by search_files tree traversal tests
- Dual-path mutation tools (move_file, copy_file) need separate backend detection per path, cross-backend check before get_backend(), and per-path MockBackend (with _exists_map dict instead of single _exists_result bool)
- S3 tools access botocore client via s3_backend.fs.s3 chain; MockS3Backend uses **kwargs on botocore methods to avoid ruff N803 naming violations from PascalCase botocore parameters

## Key Decisions
- mamba-mcp-fs follows the same package scaffold pattern as mamba-mcp-postgres
- CLI entry point registered as `mamba-mcp-fs` pointing to `mamba_mcp_fs.__main__:app`
- `no_args_is_help=True` for the Typer app since server startup is not yet implemented
- mamba-mcp-fs error framework uses plain dicts (not Pydantic models) for error responses, and adds custom exception classes (FSError base + 10 subclasses) that postgres version lacks
- Content detection uses stdlib `mimetypes` as primary with optional `python-magic` fallback; no hard dependency on libmagic
- Extra MIME map covers code file extensions (.py, .rs, .go, .ts, etc.) and dotfiles (.env, .gitignore) that stdlib mimetypes doesn't handle well
- Text vs binary classification uses MIME type prefix check first, then null-byte heuristic on first 8KB of content
- `PurePosixPath.suffix` returns empty string for dotfiles like `.env`; need to match on full filename for those
- Pydantic models use `computed_field` for `size_pretty` rather than a stored field -- ensures it stays in sync with `size_bytes` and appears in JSON serialization
- FileInfo uses composition of all FileEntry fields (not inheritance) since Pydantic computed_field and inheritance can have quirks; keeps models flat and explicit
- Response models embed references to data models (e.g. ListDirectoryResponse uses list[FileEntry]) for type safety and reuse
- Config uses field_validator for base_path emptiness check (runs always) + model_validator for existence check (only when enabled=True), allowing disabled local backend with nonexistent path
- Security: Path sandbox validation uses string prefix check with trailing "/" to prevent /sandbox-evil matching /sandbox
- Security: URL decoding loops until stable (handles double/triple encoding); null bytes stripped; NFC unicode normalization applied
- Security: S3 path normalization uses posixpath.normpath to collapse .. components (PurePosixPath does not resolve ..)
- Security: Symlink check uses path.resolve() which follows the entire chain, catching nested symlinks
- BackendManager: get_backend() returns (backend_instance, resolved_path) tuple; security validation is baked into get_backend so callers always get pre-validated paths
- BackendManager: FSError subclasses from security (PathOutsideSandboxError, etc.) are wrapped in BackendError; only BackendNotConfiguredError and BackendError pass through unwrapped
- BackendProtocol: 11 methods matching fsspec interface (ls, info, cat_file, pipe_file, rm, cp_file, mv, mkdir, exists, isdir, isfile)
- Tool functions must unwrap BackendError.__cause__ to surface original FSError code (e.g. PATH_OUTSIDE_SANDBOX) instead of generic BACKEND_ERROR
- get_file_info uses original user path for response name (os.path.basename(path)) instead of backend's resolved name, because symlink resolution changes the name
- read_file: ContentDecodeError (an FSError subclass) is raised inside _encode_content and caught by the tool's FSError handler, so it surfaces as a CONTENT_DECODE_ERROR error response automatically
- read_file: is_truncated tracks whether the file exceeds the size limit but a chunk was served (is_chunked AND total_size > size_limit), distinct from has_more (whether more data exists after the current chunk)
- read_file: _get_size_limit helper selects max_file_size from the appropriate backend settings (local or s3) based on backend_name
- write_file: read-only check is at tool level (before backend operations), not at backend level -- allows clear early rejection with PERMISSION_DENIED error code
- write_file: extension validation done at tool level in addition to LocalBackend.pipe_file() for cleaner error surfaces
- write_file: overwrite protection uses backend.exists() to check; if exists() throws, conservatively treats as new file
- write_file: parent dir creation (create_parents=True) swallows mkdir errors -- pipe_file will produce a clearer error if parent is truly missing
- get_object_metadata: uses 3 botocore API calls (head_object, get_object_tagging, list_object_versions); tags/versions have graceful fallback on error; head_object 404/NoSuchKey mapped to PATH_NOT_FOUND; _parse_s3_path helper extracted to reduce duplication

## Known Issues
- `uv sync --group dev` may uninstall and reinstall packages on first run after adding a new workspace member; subsequent runs are fast
- pytest exit code 5 (no tests collected) is normal for empty test directories
- stdlib `mimetypes.guess_type` returns `application/xml` (not `text/xml`) for `.xml` files and `application/x-tar` (not `application/gzip`) for `.tar.gz` files -- platform dependent
- `PurePosixPath(".env").suffix` returns `""` so dotfiles without extensions need special handling in MIME detection
- Pydantic `computed_field` requires `# type: ignore[prop-decorator]` comment to satisfy mypy strict mode
- `PurePosixPath` does NOT resolve `..` components -- it's a pure path class. Use `posixpath.normpath` or `Path.resolve()` for actual resolution.
- LocalBackend.ls() filters hidden files based on config default BEFORE the tool layer sees them; include_hidden=True tool parameter cannot restore entries the backend already filtered when show_hidden=False. Future fix: move hidden filtering entirely to tool layer, or add include_hidden parameter to backend.ls()
- BackendManager.get_backend() resolves paths through security validation (Path.resolve() follows symlinks). Tool functions that need symlink detection (like get_file_info) must pass the original user path to backend methods, not the resolved_path from get_backend, so the backend can check symlink status pre-resolution.
- mypy attr-defined errors on s3_backend.fs.s3 are pre-existing across all S3 tools (list_buckets, get_presigned_url, get_object_metadata) since _backends dict is typed as BackendProtocol which lacks .fs attribute
